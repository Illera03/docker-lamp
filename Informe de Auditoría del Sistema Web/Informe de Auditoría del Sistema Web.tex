\section{Introducción}
Este informe detalla la auditoría de seguridad de un sistema web utilizando OWASP ZAP\footnote{OWASP ZAP (Zed Attack Proxy) es una herramienta gratuita y de código abierto diseñada para realizar pruebas de penetración y análisis de seguridad en aplicaciones web, detectando vulnerabilidades de manera automática.\cite{zap}}, con el objetivo de identificar y mitigar vulnerabilidades.
\vspace{1em}
	
\section{Metodología}
La auditoría se realizó mediante un análisis de OWASP ZAP, que generó un informe indicando las diferentes vulnerabilidades en términos de seguridad web de nuestro sistema. Sin embargo, también se han tratado ciertas vulnerabilidades que no se detectaron en la auditoría, pero que se han considerado necesarias para garantizar la seguridad.\\

Los informes generados por OWASP ZAP, tanto el inicial como el final, estarán adjuntos juntos con este documento para su revisión y comparación.
\vspace{1em}

\section{Vulnerabilidades}
\vspace{1em}
\subsection{Rotura de control de acceso}
\vspace{1em}
\textbf{¿Qué es una rotura de control de acceso?\\}
Una rotura del control de acceso ocurre cuando un sistema permite a usuarios acceder a datos, funciones o recursos para los que no tienen autorización, debido a fallos en la implementación de los permisos. Esto puede resultar en accesos no autorizados, modificaciones indebidas de datos o acciones privilegiadas que deberían estar restringidas.\\

En esta sección se han identificado dos amenazas. La primera, que ha sido detectado por OWASP ZAP, es la Ausencia de Tokens Anti-CSRF, como se puede observar en la Figura \ref{fig:control_acceso_error}. Y la segunda, es la posibilidad de modificar la URL y acceder a cuentas de usuario ajenas, permitiendo ver información confidencial y modificarla.

	\centering
	\fbox{\includegraphics[width=0.7\textwidth]{figures/control_acceso_error.png}} % Imagen con borde negro
	\caption{Error de rotura de control de acceso detectado por OWASP ZAP.}
	\label{fig:control_acceso_error}
\end{figure}
\vspace{1em}
\subsubsection{Ausencia de Tokens Anti-CSRF}
Esta vulnerablidad ocurre cuando no se implementan mecanismos como tokens anti-CSRF\footnote{CSRF: Códigos únicos generados para verificar que una solicitud proviene de una fuente legítima y no de un atacante.}  para protegerse contra ataques en los que un atacante engaña al usuario para ejecutar acciones no deseadas en una aplicación web autenticada. Estos tokens son valores únicos y aleatorios que se validan con cada solicitud para asegurar que provienen de fuentes confiables. Sin ellos, las aplicaciones son susceptibles a ataques de tipo CSRF, donde un atacante podría realizar acciones en nombre de un usuario sin su consentimiento.\\

\textbf{Causa de la Vulnerabilidad}

La vulnerabilidad se originaba en los archivos \code{login.php}, \code{register.php}, \code{add\_item.php} y \code{modify\_user.php} y fue causada por la falta de la generación del token anti-CSRF en pestañas sensibles en las que hay que rellenar un formulario.

\vspace{1em}

\textbf{Pruebas y comportamiento observado}

El error identificado fue detectado por OWASP ZAP al capturar la solicitud original enviada por el navegador al interactuar con el formulario. Posteriormente, OWASP ZAP envió una solicitud idéntica sin incluir campos adicionales (como un token anti-CSRF), y esta fue aceptada por el servidor como si se tratara de una solicitud legítima.

\vspace{1em}

\subsubsection{Exposición y modificación de datos en la URL}

En gran parte de las URLs del sistema se mostraba información que además podía ser modificada.\\

\textbf{Causa de la Vulnerabilidad}

Se detectó que los identificadores sensibles, como los id de usuarios y juegos, se transmitían en texto plano a través de las URLs en archivos como \code{items.php} y \code{show\_item.php}. Esto exponía información crítica que podía ser utilizada para acceder o manipular recursos restringidos.
\vspace{1em}

\textbf{Pruebas y comportamiento observado}

La vulnerabilidad fue identificada mediante un análisis manual del tráfico HTTP \footnote{HTTP es un protocolo de la capa de aplicación para la transmisión de documentos hipermedia, como HTML.}(Hypertext Transfer Protocol) y de las URLs generadas por el sistema. Este análisis reveló que identificadores sensibles se transmitían en texto plano, exponiendo potencialmente datos críticos a ataques de enumeración de IDs o manipulación maliciosa.

\vspace{1em}
\newpage
\subsubsection{Soluciones implementadas}
Para minimizar la utilización de CORS\footnote{CORS: Mecanismo que permite que los recursos de un servidor sean accesibles desde diferentes dominios de manera controlada.}, se ha integrado el uso de tokens anti-CSRF con el fin de implementar mecanismos de acceso únicos.\\
\begin{itemize}
	\item \textbf{Integración de tokens anti-CSRF\\} Se ha implementado la creación de los tokens en archivos donde se manejan formularios o se ingresan los identificadores y contraseñas de los usuarios. Esto incluye archivos como \code{login.php}, \code{register.php}, \code{add\_item.php} y \code{modify\_user.php}.
	\begin{enumerate}
		\item \textbf{Generación del token anti-CSRF\\} Si no existe ya un token CSRF en la sesión \code{\$\_SESSION['csrf\_token']}, se genera uno nuevo usando \code{bin2hex(random\_bytes(32))}. Con esto se asegura que cada sesión tiene un token único y difícil de adivinar.
		\item \textbf{Uso del token en el formulario\\} En el formulario HTML\footnote{HTML: Lenguaje de marcado utilizado para estructurar y organizar el contenido en las páginas web.} (HyperText Markup Language)(\code{login.html}), este token se debe enviar como un campo oculto. Esto permite que el servidor valide que el formulario fue enviado desde la misma aplicación.
		\item \textbf{Validación del token en el servidor\\} Cuando el formulario se envía, el código verifica si el token recibido \\ (\code{\$\_POST['csrf\_token']}) coincide con el que está almacenado en la sesión. Si no coinciden o el token no existe, la solicitud se considera no válida y se bloquea (\code{die("Error de validación CSRF");}).
		\item \textbf{Eliminación del token\\}Una vez que el usuario inicia sesión correctamente, el token se elimina usando el comando \code{unset}(\code{\$\_SESSION['csrf\_token']}). Esto asegura que no pueda ser reutilizado.
	\end{enumerate}
	\item \textbf{Cifrado de URL\\} Se ha implementado el cifrado de identificadores sensibles en las URL para garantizar que los datos críticos no se expongan en texto plano. Esto incluye id de usuarios y otros identificadores que podrían ser utilizados por atacantes para realizar accesos no autorizados.
	\begin{enumerate}
		\item \textbf{Cifrado de identificadores\\} Los identificadores sensibles, como el id de usuario, son cifrados utilizando el algoritmo \code{AES-256-CBC}\cite{AES}. Este método asegura que los datos cifrados sean ilegibles sin la clave de descifrado correspondiente. El código se genera usando \code{openssl\_encrypt()} y se almacena en formato \code{base64}.
		\item \textbf{Descifrado de URL en el servidor\\} Cuando el servidor recibe una URL que contiene un identificador cifrado, este es descifrado mediante el algoritmo \code{AES-256-CBC} y la misma clave utilizada para cifrarlo. Si el descifrado falla o el identificador no es válido, se bloquea el acceso al recurso solicitado.
		\item \textbf{Uso del cifrado en enlaces\\} En archivos como \code{login.php}, \code{items.php} y \code{show\_user.php}, los identificadores que se incluyen en los enlaces son cifrados antes de enviarse al cliente. Esto asegura que el cliente nunca vea un identificador en texto plano en la URL.
		\item \textbf{Validación de identificadores cifrados\\} Los identificadores descifrados son validados en el servidor para garantizar que sean valores enteros válidos (\code{intval(\$id)}). Si no lo son, la solicitud se rechaza de inmediato para prevenir posibles ataques.
	\end{enumerate}
\end{itemize}

\vspace{1em}


\textbf{Resultados de la segunda auditoría}

Después de implementar las soluciones descritas, se realizó un segundo análisis con OWASP ZAP. Los resultados fueron positivos: no se detectaron vulnerabilidades por falta de tokens anti-CSRF.

Para el caso del cifrado de URLs, un análisis manual confirmó que los identificadores sensibles ya no se transmiten en texto plano. Las pruebas de uso del sistema mostraron que las URLs generadas contenían identificadores cifrados, que eran correctamente descifrados en el servidor antes de cualquier operación.

\vspace{1em}

\textbf{Conclusiones}

La integración de tokens anti-CSRF resolvió las vulnerabilidades detectadas en el control de acceso, garantizando que las solicitudes al servidor sean legítimas y protegidas contra ataques. Esta implementación fortaleció la seguridad en archivos clave como \code{login.php} y \code{register.php}, eliminando las fallas detectadas en la primera auditoría. La segunda evaluación con OWASP ZAP confirmó la efectividad de estas medidas, mejorando significativamente la protección del sistema.

Adicionalmente, el cifrado de URLs eliminó la exposición de identificadores sensibles en texto plano, mitigando posibles ataques relacionados con la enumeración o manipulación de IDs. Esto incrementó la seguridad de archivos como \code{items.php} y \code{show\_item.php}, contribuyendo a un acceso más seguro a los recursos del sistema.

\subsection{Fallos criptográficos}
En esta sección se comentarán los fallos de seguridad web relacionados con la criptografía\footnote{Práctica que consiste en proteger información mediante el uso de algoritmos codificados, Hashes y firmas.} (o la falta de esta) que causan la exposición de datos sensibles\cite{Fallos Criptograficos}.\\ 

Se han identificado y solucionado dos fallos criptográficos. El primer fallo consiste en almacenar la información de la base de datos sin cifrar, utilizando únicamente el cifrado de datos en reposo incorporado por la base de datos por defecto, el cual se descifra directamente al realizar una consulta\cite{MariaDB Cifrado}. El segundo fallo detectado es almacenar las contraseñas en texto plano.


\vspace{1em}
\subsubsection{Soluciones implementadas}
Para subsanar el primer error se ha decidido cifrar la información que se almacena en la base de datos. El algoritmo de cifrado simétrico\footnote{Método de cifrado que usa la misma clave para cifrar y descifrar.} que se ha usado es el AES (Advanced Encryption Standar) de 256 bits de longitud, puesto que este algoritmo es considerado seguro a día de hoy\cite{AES}.\\

El uso de este algoritmo requiere una clave segura para cifrar y descifrar los datos. Para ello se ha usado una función\cite{generador_claves_python} de Python\footnote{Lenguaje de programación orientado a objetos usado principalmente para el desarrollo web y de aplicaciones informáticas.} que genera la clave usando la librería \code{secrets}, que es una librería que genera números aleatorios con la suficiente entropía para  que la clave generada pueda ser considerada criptográficamente fuerte\cite{secrets Python}. 
Una vez generada la clave de secreta se guarda como una variable de entorno\footnote{Las variables de entorno son variables disponibles para un programa/aplicación de forma dinámica durante el tiempo de ejecución. El valor de estas variables puede proceder de diversas fuentes: archivos de texto, gestores secretos de terceros, scripts de llamada, etc.\cite{Variable de entorno}} en un archivo .env llamado \code{claveCifrado.env} para evitar comprometerla. Los datos cifrados de la tabla Juegos son el nombre, género, fecha de lanzamiento, valoración y precio. Mientras que los datos cifrados de la tabla Usuarios son el nombre, teléfono, DNI y fecha de nacimiento. Sin embargo, como al cifrar los datos su número de caracteres aumenta, se han tenido que cambiar los tipos de dato y la longitud de los campos de la base de datos para poder almacenarlos.\\ 

Para solventar el segundo error se ha decidido usar un algoritmo resumen para generar el resumen criptográfico o Hash\footnote{Criptograma que consiste en una sucesión de caracteres alfanuméricos que representan la totalidad del contenido original.} de la contraseña en vez de guardarla como texto plano. Para ello se ha usado la función \code{password\_hash} a la que se le pasa como parámetros la contraseña a resumir y una constante de PHP\footnote{PHP es un lenguaje de código abierto especialmente adecuado para el desarrollo web y que puede ser incrustado en HTML.\cite{def_php}} (Hypertext Preprocessor) \code{PASSWORD\_BCRYPT} que indica que queremos usar el algoritmo Bcryt\cite{Bcrypt}. Bcrypt usa sales \footnote{Caracteres aleatorios que se le añaden a la contraseña para que sea mas difícil precalcular los resúmenes criptográficos.} para mayor seguridad ya que hace que dos contraseñas iguales de usarios diferentes generen resúmenes criptográficos distintos, por lo que se hace mucho mas difícil precalcularlos.\\ 
\\\textbf{Conclusiones}\\
Subsanar los fallos criptográficos es una tarea fundamental para garantizar la confidencialidad y la confianza en sistemas web. Además, estas vulnerabilidades pueden llevar a la pérdida de confianza de los usuarios y a sanciones legales por no cumplir la Ley de Protección de Datos\cite{Ley proteccion de datos}.\\ 

Finalmente, se ha conseguido abordar de manera efectiva ambos fallos criptográficos gracias a las medidas implementadas, mejorando significativamente la protección de datos y la fiabilidad del sistema web. 
\vspace{1em}

\subsection{Inyección}
\vspace{1em}

\textbf{¿Qué es la inyección?\\}
La inyección es una vulnerabilidad de seguridad en la que un atacante introduce datos maliciosos en una aplicación, a menudo mediante campos de entrada o URL, logrando manipular comandos o consultas dentro del sistema. Esto permite ejecutar código no autorizado, acceder a datos sensibles o modificar información sin permisos\cite{owasp_injection}. \\

En esta sección se han identificado dos amenazas de alto riesgo. Las vulnerabilidades detectadas corresponden a una Inyección SQL y a un ataque de Cross-Site Scripting (XSS) Reflejado, como se puede observar en la Figura \ref{fig:xss_error}.

	\centering
	\fbox{\includegraphics[width=0.7\textwidth]{figures/injection-error.png}} % Imagen con borde negro
	\caption{Errores de inyección detectados por OWASP ZAP.}
	\label{fig:xss_error}

\vspace{1em}

\subsubsection{Cross-Site Scripting (XSS)}
La vulnerabilidad CWE-79 corresponde a Cross-Site Scripting (XSS) Reflejado, que permite a un atacante inyectar código malicioso en los parámetros de entrada del sistema, como los campos de formularios o las URL. Cuando un usuario accede a una URL o un formulario que contiene este código inyectado, el navegador del usuario ejecuta dicho código, lo que puede llevar a la manipulación de datos, el robo de cookies, la ejecución de scripts no autorizados, y otros ataques de seguridad.\cite{owasp_xss}

\vspace{1em}

\textbf{Causa de la vulnerabilidad}

La vulnerabilidad XSS detectada se originaba en el archivo \code{modify\_item.php}, más concretamente en el campo de la fecha de lanzamiento y en otros campos de entrada en el formulario de modificación de un juego. Esto se debía a que los valores de entrada eran reflejados en la respuesta sin la sanitización\footnote{Sanitización se refiere al proceso de limpiar o filtrar los datos de entrada para eliminar cualquier contenido malicioso que pudiera comprometer la seguridad del sistema.\cite{def_sanitization_escaping}} o validación adecuada, permitiendo a los atacantes inyectar y ejecutar código en el navegador del usuario.

\vspace{1em}

\textbf{Pruebas y comportamiento observado}

Sin la sanitización de entrada OWASP ZAP detectó que ciertos campos permitían la inyección de código en los valores de los formularios. Por ejemplo, en el campo de la fecha, se podía ingresar un valor como \code{<script>alert(1);</script>}, lo cual provocaba la ejecución de una alerta en el navegador.

\vspace{1em}

\subsubsection{Inyección SQL}
La vulnerabilidad CWE-89 corresponde a la inyección SQL, donde un atacante es capaz de insertar o manipular consultas SQL a través de los datos de entrada, en este caso, el parámetro \code{id} en la URL. 

\vspace{1em}

\textbf{Causa de la Vulnerabilidad}
 
La vulnerabilidad detectada se originaba en el archivo \code{show\_user.php} y fue causada por la construcción dinámica de consultas SQL sin la adecuada sanitización ni parametrización de los datos proporcionados por el usuario. En este caso, el valor del parámetro id se concatenó directamente a la consulta SQL sin protección, lo que permitió la ejecución de código SQL malicioso.

\vspace{1em}

\textbf{Pruebas y comportamiento observado}

En el error encontrado, la inyección fue posible al modificar el parámetro de la siguiente manera: \code{1750' AND '1'='1' --}.\\
Esto permitió a OWASP ZAP modificar la consulta SQL ejecutada en el servidor, manipulando los resultados devueltos y accediendo a información que no debía ser revelada. En particular, se manipuló la consulta para obtener datos utilizando una condición booleana que siempre era verdadera, \code{'1'='1'}, y luego se comentó el resto de la consulta utilizando \code{--}, lo que invalidaba el resto de la consulta SQL.

\vspace{1em}

\subsubsection{Soluciones implementadas}
Para mitigar la vulnerabilidad de XSS se implementaron las siguientes soluciones:

\begin{itemize}
	\item \textbf{Escapado\footnote{Escapado se refiere al proceso de transformar caracteres especiales en una entrada válida para que no sean interpretados como parte del código ejecutable.\cite{def_sanitization_escaping}} de salida:\\}
	Se utilizó la función \code{htmlspecialchars()} en PHP para escapar caracteres especiales (como <, >, \&, ", ') en todas las salidas. Esto asegura que el contenido reflejado en el navegador sea tratado como texto y no como código ejecutable.
	
	\item \textbf{Validación y sanitización de fecha de lanzamiento:\\} 
	Se implementó una expresión regular (\code{preg\_match}) para asegurarse de que las fechas ingresadas cumplan con el formato \code{YYYY-MM-DD}.
	
	\item \textbf{Sanitización de datos entrantes:\\} 
	Para cada valor de entrada recibido a través del formulario, se aplicó \\ \code{mysqli\_real\_escape\_string()} para evitar que cualquier código especial o malicioso llegue a la base de datos.
	
	\item \textbf{Validación de Campos Numéricos (rating y price):\\} 
	Los valores de rating y price se convirtieron a tipo float usando \code{floatval()} para asegurarse de que se almacenan y procesan correctamente como valores numéricos.
\end{itemize}
Para mitigar la vulnerabilidad de Inyección SQL se implementaron las siguientes soluciones:
\begin{itemize}
	\item \textbf{Uso de consultas preparadas:\\}
	Se ha utilizado el enfoque de consultas preparadas con declaraciones \code{bind\_param()}. Esto asegura que los parámetros sean tratados de forma segura, separando los datos del código SQL, y evitando así que cualquier entrada maliciosa pueda modificar la estructura de las consultas.
	\item \textbf{Validación y sanitización de entradas\\} Además de las consultas preparadas, se valida y filtra las entradas del usuario para asegurarse de que solo se acepten datos válidos. Por ejemplo, el uso de \code{intval()} para el parámetro id convierte cualquier valor no numérico a un valor seguro (como 0), evitando que se inyecten datos inesperados en las consultas.
\end{itemize}
Todas estas soluciones también se han implementado en otros archivos que, aunque no presentaban errores en el análisis, tenían vulnerabilidades relacionadas con la inyección que necesitaban ser abordadas.

\vspace{1em}

\textbf{Resultados de la segunda auditoría}

Después de implementar las soluciones descritas, se realizó un segundo análisis con OWASP ZAP. Los resultados fueron positivos: no se detectaron vulnerabilidades de XSS ni otros problemas de inyección.

\vspace{1em}

\textbf{Conclusiones}

Ambas vulnerabilidades fueron una amenaza crítica para el sistema, ya que podía permitir a los atacantes ejecutar código malicioso en el navegador de los usuarios o insertar consultas SQL a través de los datos de entrada. Gracias a las soluciones implementadas, las vulnerabilidades se han mitigado de manera efectiva. El sistema web ahora cumple con un estándar de seguridad más alto, protegiendo los datos frente a posibles ataques de inyección de código.

\subsection{Diseño inseguro}

\textbf{¿Que significa diseño inseguro?\\}
Una página web tiene un diseño inseguro cuando su estructura, funcionalidades, o configuración comprometen la seguridad de los usuarios o de sus datos. Esto puede deberse a malas prácticas en el desarrollo, falta de medidas de seguridad adecuadas o errores en la implementación.\\

Esta se situaba en la página incial, haciendo que cualquier usuario de la página, sin ni siquiera haberse registrado, pudiera ver, añadir, modificar o eliminar algún juego de la base de datos.

\subsection{Configuración de seguridad insuficiente}
\vspace{1em}

\textbf{¿Qué es la configuración de seguridad insuficiente?\\}
La configuración de seguridad insuficiente ocurre cuando un sistema o aplicación utiliza configuraciones predeterminadas, credenciales simples o no establece medidas de protección adecuadas contra posibles amenazas. Esto puede incluir la falta de restricciones de acceso, configuraciones inadecuadas de servicios, y uso de contraseñas débiles o predeterminadas \cite{sec_mis}.\\

En esta sección se ha detectado una vulnerabilidad principal, el uso de credenciales (usario y contraseña) por defecto o extremadamente simples.
\subsubsection{Credenciales por defecto}
Esta vulnerabilidad se veía reflejada en dos de nuestros servicios, MariaDB\footnote{MariaDB es un sistema de gestión de bases de datos relacionales (RDBMS) gratuito y de código abierto} y phpMyAdmin\footnote{PhpMyAdmin es una aplicación web que sirve para administrar bases de datos MySQL de forma sencilla y con una interfaz amistosa}.\\
\begin{itemize}
\item Credenciales de MariaDB:\\
Usuario: admin\\
Contraseña: test\\
\item Al igual que en phpMyAdmin:\\
Usuario: admin\\
Contraseña: test\\
\end{itemize}
Estas credenciales son extremadamente simples y no cumplen con las políticas básicas de seguridad para la autenticación. Y además, dejan expuestos servicios críticos, aumentando significativamente el riesgo de ataques como la inyección SQL, robo de datos y escalamiento de privilegios.
\vspace{1em}
\subsubsection{Soluciones implementadas}
Para mitigar este problema, se han modificado tanto los usuarios como las contraseñas de ambos servicios por unos valores más seguros. Las nuevas contraseñas cuentan con más de 10 dígitos entre los que se incluyen combinaciones de mayúsculas, minúsculas, números y caracteres especiales.\\

\textbf{Conclusiones}

El uso de credenciales predeterminadas o débiles representaba un riesgo crítico para la seguridad del sistema, ya que las anteriores eran especialmente conocidas y fáciles de explotar por atacantes. Esto facilitaba y posibilitaba el acceso no autorizado a servicios clave como MariaDB y phpMyAdmin, comprometiendo la integridad y confidencialidad de los datos.

\subsection{Fallos de identificación y autenticación}
\vspace{1em}
\textbf{¿Qué es un fallo de identificación y autenticación?\\}
Un fallo de identificación ocurre cuando el sistema no reconoce quién dices ser. Esto puede deberse a varias razones, como ingresar datos incorrectos o inexistentes, que el sistema no busque correctamente el usuario en la base de datos, o incluso por el uso de mensajes de error ambiguos o confusos que no ayudan al usuario a identificar el problema. \\ \\
\textbf{¿Cómo ocurre un ataque por fallos de identificación o autenticación?\\}
Esta vulnerabilidad se da cuando un atacante obtiene una lista de usuarios y contraseñas que pueden ser válidas en el sistema, y luego intenta acceder a las cuentas mediante un proceso automatizado. Un ejemplo común es el ataque de Credential stuffing. En este ataque, el atacante utiliza credenciales filtradas de otros servicios donde los usuarios han utilizado las mismas contraseñas, y las prueba en el sistema objetivo para obtener acceso a sus cuentas. Si el sistema no implementa medidas adicionales de seguridad, como la autenticación multifactor\footnote{Autenticación multifactor se refiere a un método de autenticación que requiere que el usuario proporcione dos o más factores de verificación diferentes para acceder a un sistema} o límites de intentos de acceso fallidos, el atacante puede obtener acceso a las cuentas de usuario con relativa facilidad.
\vspace{1em}
\subsubsection{Soluciones implementadas}

Para reducir los riesgos de los errores en la identificación y autenticación se ha implementado la siguiente solución:\\

\textbf{Bloqueo temporal de usuarios por Logins\footnote{Proceso mediante el cual un usuario se identifica y autentica en un sistema, servicio o aplicación.} fallidos:}

Se ha implementado un sistema de bloqueo temporal con ayuda de un archivo .log\footnote{Un .log es  un archivo de texto que se utiliza para registrar eventos, actividades o mensajes de un sistema, programa o aplicación} (la creación de este archivo se menciona en el apartado 3.9). Este permite registrar aquellos usuarios que han fallado 5 veces el inicio de sesión en los últimos 10 minutos. Dicha cuenta se bloquea por 10 minutos y si el usuario intenta hacer nuevamente un Login, se le mostrará el tiempo que le falta para que pueda volver a realizar otros 5 intentos. Esto se logra gestionar en el archivo.log con la función: \code{function checkFailedAttempts(email, log\_file, max\_attempts = 5, lock\_time = 600)}.

Sin embargo, es importante considerar como posible mejora la implementación de mecanismos como autenticación multifactor y sistemas de alerta para accesos sospechosos.

\subsection{Fallos en la integridad de datos y software}
\vspace{1em}
\textbf{¿Qué son los fallos en la integridad de datos y software?\\}
Se refieren a vulnerabilidades que surgen cuando un sistema, aplicación o infraestructura no cuenta con mecanismos adecuados para garantizar que el software y los datos se mantengan libres de manipulaciones no autorizadas. Estas fallas pueden manifestarse en diversas formas, como el uso de componentes no confiables o actualizaciones automáticas inseguras. El problema radica en que la falta de controles para verificar la autenticidad y la integridad permite a actores maliciosos inyectar código o alterar datos, comprometiendo el sistema y su confiabilidad \cite{fallos_integ}.\\

En esta sección no se ha encontrado ninguna vulnerabilidad principal, pero una causa común es el uso de bibliotecas o software no confiables. Esto es porque las dependencias sin verificar pueden contener vulnerabilidades o código malicioso.\\ 

Por ello, cabe mencionar que en el desarrollo del sistema actual, se utiliza la librería \code{secrets} de Python para la generación de datos aleatorios seguros. Pero esta librería, al ser parte de la biblioteca estándar de Python, es confiable y no introduce riesgos de integridad ya que sigue prácticas sólidas de generación de números pseudoaleatorios seguros para criptografía \cite{secrets Python}.

\subsection{Fallos en la monitorización de la seguridad}
\vspace{1em}
\textbf{¿Qué son los fallos en la monitorización de la seguridad?\\}
Se refieren a la ausencia o insuficiencia de registros (logs) y sistemas de monitorización necesarios para identificar, alertar y responder a incidentes de seguridad en un sistema. Estas fallas dificultan la detección temprana de actividades sospechosas, lo que puede prolongar el tiempo en el que un ataque permanece sin ser detectado. Además, la falta de registros adecuados complica la investigación posterior de incidentes y la comprensión de su alcance \cite{fallos_monit}. \\

En está sección, se contaba con una vulnerabilidad principal, ya que se carecía de un registro de logs del sistema.
\subsubsection{Soluciones implementadas}

Para mitigar la vulnerabilidad comentada se ha implementado la siguiente solución.\\

\textbf{Registro de todos los intentos de sesiones (logs):}

Se ha utilizado un archivo .log para poder gestionar y observar los intentos de sesiones y el por qué de los errores. En el archivo .log se resgistra lo siguiente:
\begin{enumerate}
	\item Fecha y hora en formato yyyy-mm-dd hh:mm:ss.
	\item SUCCESS o FAILED.
	\item Email registrado o no en la base de datos.
	\item IP\footnote{IP: Identificador único que se asigna a cada dispositivo conectado a una red}.
\end{enumerate} 

\textbf{Conclusiones}

Al registrar información clave como la fecha, hora, estado del intento (SUCCESS o FAILED), y direcciones IP involucradas, se facilita el análisis forense en caso de incidentes de seguridad. Esto también sienta las bases para implementar medidas de seguridad adicionales, como el bloqueo automático de IPs sospechosas o la aplicación de políticas más estrictas para la gestión de contraseñas.
\section{Conclusiones finales}

El análisis realizado al sistema web ha permitido identificar y corregir vulnerabilidades significativas, logrando mitigar dos de ellas de riesgo alto y una de riesgo medio. \\

Sin embargo, es importante señalar que la gran mayoría de problemas solucionados no fueron detectados por una herramienta automática como OWASP ZAP, lo que resalta la relevancia del conocimiento y el análisis manual para identificar riesgos específicos que podrían pasar desapercibidos. Además estas vulnerabilidades no eran pequeñas amenazas del sistema, si no grandes fallas de seguridad.

A pesar de los logros alcanzados, persisten dos vulnerabilidades clasificadas como de riesgo medio. Su resolución implica modificaciones en la imagen web del sistema, lo que requiere unas modificaciones extra. Aunque no representan una amenaza alta, su existencia es un problema y debería ser objeto de mejora en el futuro.

En conclusión, la auditoría ha resultado en mejoras significativas en la seguridad del sistema web, pero también evidencia la necesidad de un enfoque continuo y equilibrado.Y por lo observado, es crucial combinar herramientas automáticas con revisiones manuales y un  estudio continuo de posibles vulnerabilidades.
