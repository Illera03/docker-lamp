\subsection{Rotura de control de acceso}
Una rotura del control de acceso ocurre cuando un sistema permite a usuarios acceder a datos, funciones o recursos para los que no tienen autorización, debido a fallos en la implementación de los permisos. Esto puede resultar en accesos no autorizados, modificaciones indebidas de datos o acciones privilegiadas que deberían estar restringidas.
\vspace{1em}
\subsubsection{Soluciones implementadas}
Para minimizar la utilización de CORS\footnote{CORS: Mecanismo que permite que los recursos de un servidor sean accesibles desde diferentes dominios de manera controlada.}, se ha integrado el uso de tokens CSRF\footnote{CSRF: Códigos únicos generados para verificar que una solicitud proviene de una fuente legítima y no de un atacante.} con el fin de implementar mecanismos de acceso únicos.\\
\begin{itemize}
\item \textbf{Integración de tokens CSRF\\} Se ha implementado la creación de los tokens en archivos donde se manejan formularios o se ingresan los identificadores y contraseñas de los usuarios. Esto incluye archivos como \code{login.php}, \code{register.php}, \code{add\_item.php} y \code{modify\_user.php}.
\begin{enumerate}
\item \textbf{Generación del token CSRF\\} Si no existe ya un token CSRF en la sesión \code{\$\_SESSION['csrf\_token']}, se genera uno nuevo usando \code{bin2hex(random\_bytes(32))}. Con esto se asegura que cada sesión tiene un token único y difícil de adivinar.
\item \textbf{Uso del token en el formulario\\} En el formulario HTML\footnote{Lenguaje de marcado utilizado para estructurar y organizar el contenido en las páginas web.} (HyperText Markup Language)(\code{login.html}), este token se debe enviar como un campo oculto. Esto permite que el servidor valide que el formulario fue enviado desde la misma aplicación.
\item \textbf{Validación del token en el servidor\\} Cuando el formulario se envía, el código verifica si el token recibido \\ (\code{\$\_POST['csrf\_token']}) coincide con el que está almacenado en la sesión. Si no coinciden o el token no existe, la solicitud se considera no válida y se bloquea (\code{die("Error de validación CSRF");}).
\item \textbf{Eliminación del token\\}Una vez que el usuario inicia sesión correctamente, el token se elimina usando el comando \code{unset}(\code{\$\_SESSION['csrf\_token']}). Esto asegura que no pueda ser reutilizado.
\end{enumerate}
\end{itemize}

\subsection{Fallos criptográficos}
En esta sección se comentarán los fallos de seguridad web relacionados con la criptografía\footnote{Práctica que consiste en proteger información mediante el uso de algoritmos codificados, Hashes y firmas.} (o la falta de esta) que causan la exposición de datos sensibles\cite{Fallos Criptograficos}.\\ \\
Se han identificado y solucionado dos fallos criptográficos. El primer fallo consiste en almacenar la información de la base de datos sin cifrar, utilizando únicamente el cifrado de datos en reposo incorporado por nuestra base de datos, el cual se descifra directamente al realizar una consulta\cite{MariaDB Cifrado}. El segundo fallo detectado es almacenar las contraseñas en texto plano.

\subsection{Inyección}
\vspace{1em}

\textbf{¿Qué es la inyección?\\}
La inyección es una vulnerabilidad de seguridad en la que un atacante introduce datos maliciosos en una aplicación, a menudo mediante campos de entrada o URL, logrando manipular comandos o consultas dentro del sistema. Esto permite ejecutar código no autorizado, acceder a datos sensibles o modificar información sin permisos\cite{owasp_injection}. \\

En esta sección se han identificado dos amenaza de alto riesgo. Las vulnerabilidades detectadas corresponden a una Inyección SQL y a un ataque de Cross-Site Scripting (XSS) Reflejado, como se puede observar en la Figura \ref{fig:xss_error}.

\subsubsection{Cross-Site Scripting (XSS)}
La vulnerabilidad CWE-79 corresponde a Cross-Site Scripting (XSS) Reflejado, que permite a un atacante inyectar código malicioso en los parámetros de entrada del sistema, como los campos de formularios o las URL. Cuando un usuario accede a una URL o un formulario que contiene este código inyectado, el navegador del usuario ejecuta dicho código, lo que puede llevar a la manipulación de datos, el robo de cookies, la ejecución de scripts no autorizados, y otros ataques de seguridad.\cite{owasp_xss}

\vspace{1em}

\textbf{Causa de la vulnerabilidad}

La vulnerabilidad XSS detectada se originaba en el archivo \code{modify\_item.php}, más concretamente en el campo de la fecha de lanzamiento y en otros campos de entrada en el formulario de modificación de un juego. Esto se debía a que los valores de entrada eran reflejados en la respuesta sin la sanitización o validación adecuada, permitiendo a los atacantes inyectar y ejecutar código JavaScript en el navegador del usuario.

\vspace{1em}

\textbf{Pruebas y comportamiento observado}

Sin la sanitización de entrada: OWASP ZAP detectó que ciertos campos permitían la inyección de código JavaScript en los valores de los formularios.\\ Por ejemplo, en el campo de la fecha, se podía ingresar un valor como \\\code{<script>alert(1);</script>}, lo cual provocaba la ejecución de una alerta en el navegador.

\vspace{1em}

\subsubsection{Inyección SQL}
La vulnerabilidad CWE-89 corresponde a la inyección SQL, donde un atacante es capaz de insertar o manipular consultas SQL a través de los datos de entrada, en este caso, el parámetro \texttt{id} en la URL. 

\vspace{1em}

\textbf{Causa de la Vulnerabilidad}
 
La vulnerabilidad detectada se originaba en el archivo \code{show\_user.php} y fue causada por la construcción dinámica de consultas SQL sin la adecuada sanitización\footnote{Sanitización se refiere al proceso de limpiar o filtrar los datos de entrada para eliminar cualquier contenido malicioso que pudiera comprometer la seguridad del sistema.\cite{def_sanitization_escaping}} ni parametrización de los datos proporcionados por el usuario. En este caso, el valor del parámetro \texttt{id} se concatenó directamente a la consulta SQL sin protección, lo que permitió la ejecución de código SQL malicioso.

\vspace{1em}

\textbf{Pruebas y comportamiento observado}

En el error encontrado, la inyección fue posible al modificar el parámetro de la siguiente manera: \code{1750' AND '1'='1' --}\\
Esto permitió a OWASP ZAP modificar la consulta SQL ejecutada en el servidor, manipulando los resultados devueltos y accediendo a información que no debía ser revelada. En particular, se manipuló la consulta para obtener datos utilizando una condición booleana que siempre era verdadera, \texttt{'1'='1'}, y luego se comentó el resto de la consulta utilizando \texttt{--}, lo que invalidaba el resto de la consulta SQL.

\vspace{1em}

\subsubsection{Soluciones implementadas}
Para mitigar la vulnerabilidad de XSS se implementaron las siguientes soluciones:

\begin{itemize}
	\item \textbf{Escapado\footnote{Escapado se refiere al proceso de transformar caracteres especiales en una entrada válida para que no sean interpretados como parte del código ejecutable.\cite{def_sanitization_escaping}} de salida:\\}
	Se utilizó la función \code{htmlspecialchars()} en PHP para escapar caracteres especiales (como <, >, \&, ", ') en todas las salidas. Esto asegura que el contenido reflejado en el navegador sea tratado como texto y no como código ejecutable.
	
	\item \textbf{Validación y sanitización de fecha de lanzamiento:\\} 
	Se implementó una expresión regular (\code{preg\_match}) para asegurarse de que las fechas ingresadas cumplan con el formato \code{YYYY-MM-DD}.
	
	\item \textbf{Sanitización de datos entrantes:\\} 
	Para cada valor de entrada recibido a través del formulario, se aplicó \\ \code{mysqli\_real\_escape\_string()} para evitar que cualquier código especial o malicioso llegue a la base de datos.
	
	\item \textbf{Validación de Campos Numéricos (rating y price):\\} 
	Los valores de rating y price se convirtieron a tipo float usando \code{floatval()} para asegurarse de que se almacenan y procesan correctamente como valores numéricos.
\end{itemize}
Para mitigar la vulnerabilidad de Inyección SQL se implementaron las siguientes soluciones:
\begin{itemize}
	\item \textbf{Uso de consultas preparadas:\\}
	Se ha utilizado el enfoque de consultas preparadas con declaraciones \code{bind\_param()}. Esto asegura que los parámetros sean tratados de forma segura, separando los datos del código SQL, y evitando así que cualquier entrada maliciosa pueda modificar la estructura de las consultas.
	\item \textbf{Validación y sanitización de entradas\\} Además de las consultas preparadas, se valida y filtra las entradas del usuario para asegurarse de que solo se acepten datos válidos. Por ejemplo, el uso de \code{intval()} para el parámetro id convierte cualquier valor no numérico a un valor seguro (como 0), evitando que se inyecten datos inesperados en las consultas.
\end{itemize}
Todas estas soluciones también se han implementado en otros archivos que, aunque no presentaban errores en el análisis, tenían vulnerabilidades relacionadas con la inyección que necesitaban ser abordadas.

\vspace{1em}

\textbf{Resultados de la segunda auditoría}

Después de implementar las soluciones descritas, se realizó un segundo análisis con OWASP ZAP. Los resultados fueron positivos: no se detectaron vulnerabilidades de XSS ni otros problemas de inyección.

\vspace{1em}

\textbf{Conclusiones}

Ambas vulnerabilidades fueron una amenaza crítica para la aplicación, ya que podía permitir a los atacantes ejecutar código malicioso en el navegador de los usuarios o insertar consultas SQL a través de los datos de entrada. Gracias a las soluciones implementadas, las vulnerabilidades se han mitigado de manera efectiva. La aplicación ahora cumple con un estándar de seguridad más alto, protegiendo los datos frente a posibles ataques de inyección de código.

\subsection{Configuración de seguridad insuficiente}
\vspace{1em}

\textbf{¿Qué es la configuración de seguridad insuficiente?\\}
La configuración de seguridad insuficiente ocurre cuando un sistema o aplicación utiliza configuraciones predeterminadas, credenciales simples o no establece medidas de protección adecuadas contra posibles amenazas. Esto puede incluir la falta de restricciones de acceso, configuraciones inadecuadas de servicios, y uso de contraseñas débiles o predeterminadas \cite{sec_mis}.
En esta sección se ha detectado una vulnerabilidad principal, el uso de credenciales (usario y contraseña) por defecto o extremadamente simples.
\subsubsection{Credenciales por defecto}
Esta vulnerabilidad se veía reflejada en dos de nuestros servicios, MariaDB y phpMyAdmin.\\
Credenciales de MariaDB:\\
Usuario: admin\\
Contraseña: test\\
Al igual que en phpMyAdmin:\\
Usuario: admin\\
Contraseña: test\\
Estas credenciales son extremadamente simples y no cumplen con las políticas básicas de seguridad para la autenticación. Y además, dejan expuestos servicios críticos, aumentando significativamente el riesgo de ataques como la inyección SQL, robo de datos y escalamiento de privilegios.
\vspace{1em}
\subsubsection{Soluciones implementadas}
Para mitigar este problema, se han modificado tanto los usuarios como las contraseñas de ambos servicios por unos valores más seguros. Las nuevas contraseñas cuentan con más de 10 dígitos entre los que se incluyen combinaciones de mayúsculas, minúsculas, números y caracteres especiales.\\
\vspace{1em}

\textbf{Conclusiones}

El uso de credenciales predeterminadas o débiles representaba un riesgo crítico para la seguridad del sistema, ya que las anteriores eran especialmente conocidas y fáciles de explotar por atacantes. Esto facilitaba y posivilitaba el acceso no autorizado a servicios clave como MariaDB y phpMyAdmin, comprometiendo la integridad y confidencialidad de los datos.

\subsection{Fallos de identificación y autenticación}
\vspace{1em}
\textbf{¿Qué es un fallo de identificación y autenticación?\\}
Un fallo de identificación ocurre cuando el sistema no reconoce quién dices ser. Esto puede deberse a varias razones, como ingresar datos incorrectos o inexistentes, que el sistema no busque correctamente el usuario en la base de datos, o incluso por el uso de mensajes de error ambiguos o confusos que no ayudan al usuario a identificar el problema. Además, la ausencia de mensajes claros también puede contribuir a que el sistema no reconozca correctamente al usuario.\\
Esto puede suceder porque el usuario ha registrado una contraseña insegura o fácil de adivinar, utiliza mecanismos simples para recuperar contraseñas, o bien porque no se ha implementado un sistema de autenticación más robusto como la autenticación multifactor\footnote{Autenticación multifactor se refiere a un método de autenticación que requiere que el usuario proporcione dos o más factores de verificación diferentes para acceder a un sistema}.
\\ \\
\textbf{¿Cómo ocurre un ataque por fallos de identificación o autenticación?\\}
Esta vulnerabilidad se da cuando un atacante obtiene una lista de usuarios y contraseñas que pueden ser válidas en el sistema, y luego intenta acceder a las cuentas mediante un proceso automatizado. Un ejemplo común es el ataque de Credential stuffing\footnote{Credential stuffing: Ataque cibernético en el que los atacantes usan combinaciones de nombres de usuario y contraseñas robadas de otras plataformas para intentar acceder a cuentas en diferentes sitios web o servicios.}. En este ataque, el atacante utiliza credenciales filtradas de otros servicios donde los usuarios han utilizado las mismas contraseñas, y las prueba en el sistema objetivo para obtener acceso a sus cuentas. Si el sistema no implementa medidas adicionales de seguridad, como la autenticación multifactor o límites de intentos de acceso fallidos, el atacante puede obtener acceso a las cuentas de usuario con relativa facilidad.
