\subsection{Fallos criptográficos}
En esta sección se comentarán los fallos de seguridad web relacionados con la criptografía o su ausencia.\\
Hemos identificado y solucionado dos fallos criptográficos. El primer fallo fue almacenar los datos de nuestra base de datos sin cifrar, utilizando únicamente el cifrado incorporado por SQL, el cual se descifra directamente al realizar una consulta. El segundo fallo consistió en almacenar las contraseñas en texto plano.

\subsubsection{Soluciones implementadas}
Para subsanar el primer error decidimos cifrar datos que almacenamos en nuestra base de datos. Para ello se decidió usar el algoritmo de cifrado simétrico \footnote{Método de cifrado que usa la misma clave para cifrar y descifrar} Advanced Encryption Standar (AES) de 256 bits de longitud. Puesto que este algoritmo se considera seguro.\\

Para usar este algoritmo tuvimos que generar una clave segura para cifrar y descifrar los datos. Por eso usamos un código de Python\footnote{ Lenguaje de programación orientado a objetos usado principalmente para el desarrollo web y de aplicaciones informáticas.}\cite{generador_claves_python}  para generarla usando la librería secrets, que es un modulo que genera números aleatorios con la suficiente entropía para  que la clave generada pueda ser considerada criptográficamente fuerte. Una vez generada la clave de secreta la guardamos como una variable de entorno\footnote{Las variables de entorno son variables disponibles para tu programa/aplicación de forma dinámica durante el tiempo de ejecución. El valor de estas variables puede proceder de diversas fuentes: archivos de texto, gestores secretos de terceros, scripts de llamada, etc.\cite{Variable de entorno}} en un archivo .env llamado claveCifrado.env para evitar comprometerla. Después implementamos los algoritmos de cifrado y descifrado en nuestro proyecto. Los datos de cifrado/descifrado juegos (nombre, genero, fecha de lanzamiento, valoración y precio) y de usuarios (nombre, teléfono, DNI y fecha de nacimiento) han sido cifrados. Sin embargo, como al cifrar los datos estos aumentan su número de caracteres hemos tenido que cambiar los tipos de dato y la longitud de los campos de la base de datos para poder guardalos.\\ \\
Para solventar el segundo error decidimos usar un algoritmo resumen para guardar el resumen criptográfico \footnote{Criptograma que consiste en una sucesión de caracteres alfanuméricos que representan la totalidad del contenido original} de la contraseña en vez de guardarla como texto plano. Para ello usamos la función \code{password\_hash} a la que le damos como parámetros la contraseña a resumir y un una constante de PHP \footnote{PHP es un lenguaje de código abierto especialmente adecuado para el desarrollo web y que puede ser incrustado en HTML.\cite{def_php}} (Hypertext Preprocessor) \code{PASSWORD\_BCRYPT} que indica que queremos usar el algoritmo Bcryt\cite{Bcrypt}. Además Bcrypt, usa sales \footnote{caracteres aleatorios que se le añaden a la contraseña para que sea mas difícil precalcular los resúmenes criptográficos} para mayor seguridad ya que dos usuarios con la misma contraseña tendrán resúmenes criptográficos distintos.

\subsection{Inyección}
\vspace{1em}

\textbf{¿Qué es la inyección?\\}
La inyección es una vulnerabilidad de seguridad en la que un atacante introduce datos maliciosos en una aplicación, a menudo mediante campos de entrada o URL, logrando manipular comandos o consultas dentro del sistema. Esto permite ejecutar código no autorizado, acceder a datos sensibles o modificar información sin permisos. Un tipo común de inyección es el SQL Injection, que ocurre cuando consultas SQL maliciosas son ejecutadas por la base de datos, generalmente debido a la falta de validación de entrada en la aplicación.\\

En esta sección se han identificado dos amenaza de alto riesgo. Las vulnerabilidades detectadas corresponden a una Inyección SQL y a un ataque de Cross-Site Scripting (XSS) Reflejado, como se puede observar en la Figura \ref{fig:xss_error}.

\subsubsection{Cross-Site Scripting (XSS)}
La vulnerabilidad CWE-79 corresponde a Cross-Site Scripting (XSS) Reflejado, que permite a un atacante inyectar código malicioso en los parámetros de entrada del sistema, como los campos de formularios o las URL. Cuando un usuario accede a una URL o un formulario que contiene este código inyectado, el navegador del usuario ejecuta dicho código, lo que puede llevar a la manipulación de datos, el robo de cookies, la ejecución de scripts no autorizados, y otros ataques de seguridad.\cite{owasp_xss}

\vspace{1em}

\textbf{Causa de la vulnerabilidad\\}
La vulnerabilidad XSS detectada se originaba en el archivo \code{modify\_item.php}, más concretamente en el campo de la fecha de lanzamiento y en otros campos de entrada en el formulario de modificación de un juego. Esto se debía a que los valores de entrada eran reflejados en la respuesta sin la sanitización o validación adecuada, permitiendo a los atacantes inyectar y ejecutar código JavaScript en el navegador del usuario.

\vspace{1em}

\textbf{Pruebas y comportamiento observado}

Sin la sanitización de entrada: OWASP ZAP detectó que ciertos campos permitían la inyección de código JavaScript en los valores de los formularios.\\ Por ejemplo, en el campo de la fecha, se podía ingresar un valor como \\\code{<script>alert(1);</script>}, lo cual provocaba la ejecución de un alert en el navegador.

\vspace{1em}

\subsubsection{Inyección SQL}
La vulnerabilidad CWE-89 corresponde a la inyección SQL, donde un atacante es capaz de insertar o manipular consultas SQL a través de los datos de entrada, en este caso, el parámetro \texttt{id} en la URL. 

\vspace{1em}

\textbf{Causa de la Vulnerabilidad\\} 
La vulnerabilidad detectada se originaba en el archivo \code{show\_user.php} y fue causada por la construcción dinámica de consultas SQL sin la adecuada sanitización\footnote{Sanitización se refiere al proceso de limpiar o filtrar los datos de entrada para eliminar cualquier contenido malicioso que pudiera comprometer la seguridad del sistema.\cite{def_sanitization_escaping}} ni parametrización de los datos proporcionados por el usuario. En este caso, el valor del parámetro \texttt{id} se concatenó directamente a la consulta SQL sin protección, lo que permitió la ejecución de código SQL malicioso.

\vspace{1em}

\textbf{Pruebas y comportamiento observado\\}
En el error encontrado, la inyección fue posible al modificar el parámetro de la siguiente manera: \code{1750' AND '1'='1' --}\\
Esto permitió a OWASP ZAP modificar la consulta SQL ejecutada en el servidor, manipulando los resultados devueltos y accediendo a información que no debía ser revelada. En particular, se manipuló la consulta para obtener datos utilizando una condición booleana que siempre era verdadera, \texttt{'1'='1'}, y luego se comentó el resto de la consulta utilizando \texttt{--}, lo que invalidaba el resto de la consulta SQL.

\vspace{1em}

\subsubsection{Soluciones implementadas}
Para mitigar la vulnerabilidad de XSS se implementaron las siguientes soluciones:

\begin{itemize}
	\item \textbf{Escapado\footnote{Escapado se refiere al proceso de transformar caracteres especiales en una entrada válida para que no sean interpretados como parte del código ejecutable.\cite{def_sanitization_escaping}} de salida:\\}
	Se utilizó la función \code{htmlspecialchars()} en PHP para escapar caracteres especiales (como <, >, \&, ", ') en todas las salidas. Esto asegura que el contenido reflejado en el navegador sea tratado como texto y no como código ejecutable.
	
	\item \textbf{Validación y sanitización de fecha de lanzamiento:\\} 
	Se implementó una expresión regular (\code{preg\_match}) para asegurarse de que las fechas ingresadas cumplan con el formato \code{YYYY-MM-DD}.
	
	\item \textbf{Sanitización de datos entrantes:\\} 
	Para cada valor de entrada recibido a través del formulario, se aplicó \\ \code{mysqli\_real\_escape\_string()} para evitar que cualquier código especial o malicioso llegue a la base de datos.
	
	\item \textbf{Validación de Campos Numéricos (rating y price):\\} 
	Los valores de rating y price se convirtieron a tipo float usando \code{floatval()} para asegurarse de que se almacenan y procesan correctamente como valores numéricos.
\end{itemize}
Para mitigar la vulnerabilidad de Inyección SQL se implementaron las siguientes soluciones:
\begin{itemize}
	\item \textbf{Uso de consultas preparadas:\\}
	Se ha utilizado el enfoque de consultas preparadas con declaraciones \code{bind\_param()}. Esto asegura que los parámetros sean tratados de forma segura, separando los datos del código SQL, y evitando así que cualquier entrada maliciosa pueda modificar la estructura de las consultas.
	\item \textbf{Validación y sanitización de entradas\\} Además de las consultas preparadas, se valida y filtra las entradas del usuario para asegurarse de que solo se acepten datos válidos. Por ejemplo, el uso de \code{intval()} para el parámetro id convierte cualquier valor no numérico a un valor seguro (como 0), evitando que se inyecten datos inesperados en las consultas.
\end{itemize}
Todas estas soluciones también se han implementado en otros archivos que, aunque no presentaban errores en el análisis, tenían vulnerabilidades relacionadas con la inyección que necesitaban ser abordadas.

\vspace{1em}

\textbf{Resultados de la segunda auditoría\\}
Después de implementar las soluciones descritas, se realizó un segundo análisis con OWASP ZAP. Los resultados fueron positivos: no se detectaron vulnerabilidades de XSS ni otros problemas de inyección.

\vspace{1em}

\textbf{Conclusiones}

Ambas vulnerabilidades fueron una amenaza crítica para la aplicación, ya que podía permitir a los atacantes ejecutar código malicioso en el navegador de los usuarios o insertar consultas SQL a través de los datos de entrada. Gracias a las soluciones implementadas, las vulnerabilidades se han mitigado de manera efectiva. La aplicación ahora cumple con un estándar de seguridad más alto, protegiendo los datos y la experiencia de los usuarios frente a posibles ataques de inyección de código.
